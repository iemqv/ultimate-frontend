# The project-owned handoff

Treat the record as a small contract the next contributor can check, not a report about the agent. Keep it near the project's existing design decisions. Update the affected entry rather than appending a transcript. Existing project facts stay authoritative: link to a schedule or token instead of copying a second editable version.

| Keep | Write it so another contributor can act |
| --- | --- |
| Visitor and outcome | Who must decide what? Which real item or fact resolves the decision? |
| Fixed constraints | Point to the source: brand token, content file, approved layout, accessibility requirement. Don't reclassify an agent preference as a requirement. |
| Chosen relationship | What comes first, where does the eye go next, and why? What survives on the phone? Record one meaningful trade-off, not every sketch. |
| Action and return | Describe a reproducible starting state, input, visible result and way back. Name the control by the outcome the visitor sees. |
| Verification | Only after testing: route, width, input and observed result. If unavailable, state the gap. |

For example: “A returning reader compares two editions. Keep the publication year beside each title, even when cover art moves below on narrow screens. Open a title with Enter; after Escape the same title must hold focus.” A later refinement can improve the picker without moving those years away from the choice. If the new brief genuinely changes the relationship, replace that decision and note why. Don't log colors or motions that are already expressed by project tokens.
