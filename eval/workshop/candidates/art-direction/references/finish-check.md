# Browser finish check

Use the project's preview with representative content. Capture and inspect the affected screens at widths that can expose the change: start with desktop and phone; include nearby project breakpoints and the narrowest supported width when layout changes. A scoped copy edit does not need the same matrix as a new layout. Capture relevant states rather than only the default screen. Treat a missing browser, fixture, or interaction path as an evidence gap, not a pass.

## Make a visual redline before polishing

Look at the actual pixels, first at thumbnail size and then at reading size. For a refinement, compare the affected state before and after the change and check whether the original obstacle remains. For a new layout, in the opening and the following section, point to the dominant mass, working edge, first decision, and where the eye lands next. Compare those observations to the sketch, not to adjectives in the plan. At phone width, does the subject or task still appear at the right moment, or did the interesting part move below a screen of introduction?

When something fails, write one concrete redline: **where → what happens to the visitor → what changes**. For example: “At 390px the three filters wrap above the only result; the visitor cannot see the effect of a selection. Put the count and active filter beside the first result.” Fix structure and real copy before fine spacing, color, icons and animation. Delete a repeated badge or accent when the underlying hierarchy already says the same thing. On a refinement, preserve good existing choices instead of manufacturing a before/after difference.

## Inspect what the user sees and does

1. **Read the composition.** Can you identify the current state and next action without explanation? Check hierarchy, contrast, alignment, wrapping and clipping, density, and scan order against the intended surface job. Check for placeholder claims or missing product evidence. Compare refinement work to the original screen at the same width.
2. **Exercise the main flow.** On an open brief, start without knowing which option or section to choose. Use a realistic constraint, and point to the visible fact that resolves it on desktop and phone. If you had to open every panel, remember a hidden value, or guess what a link does, fix that specific obstacle; a livelier hero won't fix it. Record the observed path, not a claim that people will be faster. Follow the real action through to its outcome. Check applicable loading, empty, error and recovery states. Inspect feedback and whether a user can back out. Distinguish a broken behavior from a difference in taste.
3. **Use alternate inputs.** Tab through affected controls and operate them with the keyboard. Check focus after an overlay closes. Verify mobile access and reduced motion where relevant. Measure contrast where uncertain: WCAG AA uses 4.5:1 for normal text and 3:1 for large text, subject to its exceptions.

For critique, anchor findings to a route, viewport, state and screenshot or observed action. State the user impact and a specific remedy. For implementation, collect findings in one pass, fix confirmed issues in scope together, then repeat only relevant checks. Don't start another broad critique unless the direction or user flow changed. Keep a short record: route, viewport, input, outcome, and missing evidence. Open the settled screenshots; merely capturing them proves nothing about the composition. Check failed assets and horizontal overflow at the narrowest supported width. Share asset credit/license information for borrowed visuals. If a real action is unavailable, label the prototype or offer a working alternative; a visit button without hours or a location is not a verified visit flow.
